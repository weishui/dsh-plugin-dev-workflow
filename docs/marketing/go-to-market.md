# 市场推广口径 · Go-to-market

> 状态：工作稿（Lead 起草）。用途：统一 README 首屏、GitHub About、npm description、市场条目、
> 社区帖子的说法；确保每个渠道「说得好听」但不越过真实能力边界。
>
> 事实来源：`index.js`（7 个 `dev_*` 工具与状态机）、`client.js` + `docs/preview-board.png`（只读看板）、
> `cordis.patch.yml`（preset persona 与运行期提醒）、`verify/smoke.mjs`（可验证的能力边界）。

| # | 版本 | 适合放在 |

## 2. 电梯稿

**60 字内**

> 选一个人设，说想法；它记原话、拆任务、跑真验证。换 session、隔一周回来，上下文都在项目里。

**200 字内**

> AI 写代码不缺能力，缺的是连续性：需求散在聊天里、决策靠回忆、验证凭感觉。
> 这个 DSH 插件把「一个人 + 一个 AI」的轻量开发串成五步——需求（原话 + 验收）、反馈（原话 + 决策）、
> 任务（步骤 + 风险）、验证（命令 + 退出码）、收口（带证据的总结）。
> 记录落在项目目录的 append-only JSONL 里，左侧边栏一块只读看板随时看四列。
> 适合插件、小工具、一个人的小应用；不适合大型多人协作研发项目。

## 3. 人群

**适合（判断信号）**

- 项目能用「我一个人 + 几个晚上」说清；
- 想法模糊，想边聊边定；
- 同一个项目横跨多个 session、几天甚至几周；
- 你被「AI 又问一遍需求」「上次那个结论呢」烦过；
- 你想要证据，但不想上 Jira / 不想要审批流。

**不适用（要主动说，说了更可信）**

- 多人协作的正式研发项目：没有角色、权限、评审、CI 集成，也没有打算做；
- 需要合规审计、跨团队流程治理；
- 期待「一句话自动生成整个产品」——它是工作协议，不是自动驾驶；
- 想要云端团队看板 —— 记录是仓库里的文件，跟着项目走。

## 4. 卖点排序（写文案时按这个顺序）

1. **不丢**（最强、最难被替代）：原话落盘 + 跨 session 摘要 + 每 5 步运行期提醒。
   证据：真机会话里 persona 不够用，`dev_request_capture` 曾拖到 +86 秒才触发，因此加了 pre-step 提醒。
2. **不失真**：`rawQuote` 存你打的字；反馈不会悄悄升级成规范（`dev_knowledge_promote` 默认 `proposed`）。
3. **有证据**：`dev_verify` 记录命令与退出码；没有通过证据，`dev_complete` 只能是 `partial`，
   没有你确认只能是 `waiting-user`。
4. **看得见**：只读看板四列（需求 / 待办 / 待确认 / 已完成），大量记录仍有窗口与计数。
5. **不越权**：不跨项目读、不自动提交、不自动发布、不自动装依赖。

顺序不要反：先讲「不丢」，再讲「有证据」。「流程管理」放最后 —— 单说流程，会被当成又一个 TODO 工具。

## 5. 三个可直接复用的体验故事

**故事一：从一句「那个东西挺好的」开始**
散步时想到「把标签页收成一个清单」。回到电脑前只剩半句，选 preset 说出口，agent 先把它抄成原话，
再追问验收：读得到当前窗口、能导出 markdown、不新增依赖。三分钟后你有了三条任务和一个说不清时能回去看的
「我当初到底想要什么」。

**故事二：隔了一周的那个下午**
新 session，第一句是「上次那个分组功能做到哪了？」`dev_context_get` 给回：需求 2 条、进行中任务 3 个、
最近一条反馈是「先按域名分，别做手动的」。你不用复述，它也不用重新猜。

**故事三：它没说「应该跑通了」**
任务收口时它给出真实命令和退出码；门禁红过一次，`verifications.jsonl` 里留着那条 `exitCode: 1`。
三周后你想知道这个功能为什么改成了另一种实现，答案在记录里，不在记忆里。

## 6. 异议处理

| 质疑 | 回应 |
| --- | --- |
| 「这不就是 TODO 列表？」 | TODO 只有「做什么」。这里还有你**原话**、你怎么否掉上一版、命令和退出码。任务只是副产品。 |
| 「JSONL 我 `cat` 不就行了？」 | 能，而且这就是设计意图：纯文本、可 `git diff`、可接自己的脚本。看板只是给「不想 `cat` 的下午」准备的只读视图。 |
| 「看板只读有什么用？」 | 因为写入应该由流程产生，而不是由你手改卡片。你改卡片 = 记录和现实脱节；改需求 = 说一句话，agent 记。 |
| 「会不会把我的聊天全存下来？」 | 只存 `dev_*` 显式登记的内容：原话、验收、决策、命令与退出码。没有后台录制，没有遥测，全在本地。 |
| 「为什么不支持多人协作？」 | 因为那是另一个产品。轻量场景里，多一层角色和权限只会让「说一句话」变成「走个流程」。 |
| 「装了插件为什么没自动记？」 | 需要在新会话里**选中 preset**「研发助手 · Dev Assistant」。preset 决定工具与 persona；提醒也由它注入。 |

## 8. 不可承诺清单（说了就反噬）

| 不能说的话 | 真实边界 |
| --- | --- |
| 「多人协作 / 团队看板」 | 记录是本地文件，没有账号、权限、同步 |
| 「云同步 / 跨设备同步」 | 只有项目目录里的文件；迁移靠拷贝仓库 |
| 「自动提交 / 自动发布」 | 明确不做；发布永远留给人（npm 还需 2FA OTP） |
| 「企业合规审计」 | 它留证据，但不是审计系统，没有留存策略与访问控制 |
| 「自动生成整个产品」 | 它是工作协议，不替你做产品决策 |
| 「完成状态是 `blocked`」 | 代码只会产出 `succeeded / waiting-user / partial`；工具描述里提过 `blocked`，但实现没有 |
| 「全自动，不需要你确认」 | 破坏性动作一定停下来问；`dev_complete` 没有 `userAck` 就是 `waiting-user` |

## 9. 节奏建议

- **现在（0.2.x）**：README 换口径 + 看板截图 + 头图，先把「轻量开发 workflow」这个词占住。
- **发 0.3 前**：补一段「我的第一天」实录（真实时间戳、脱敏），比任何形容词都有说服力。
- **每次发版**：把 `docs/log/` 里那篇踩坑记录改写成一条公开帖子 —— 真实性本身就是推广。
