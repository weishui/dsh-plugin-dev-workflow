# 2026-11-01 · 0.2.5 路由单一所有者版

0.2.4 发布当天追加：看板功能已被负责人确认可用（「完美，现在可以用了」），但插件页
`dev-workflow-host` 组件标红 Problem——「exact Fetch route '/api/dsh-dev-assistant.board'
is already registered」。功能能用（第一个所有者在服务路由），但激活失败的组件给了
红色徽标，不可接受。

## 根因

`apply()` 的 `config.board !== false` 默认分支让**每一次挂载**都注册看板路由，而
0.2.3 引入的两层挂载（宿主顶层 `dev-workflow-host` + preset 会话内嵌
`dev-assistant-tools`）意味着同一宿主里该路由最多被注册两次。connection 的 fetch
路由按 exact path 唯一，第二次注册抛「already registered」，后挂载的 fiber 整体激活
失败。谁后挂载谁标红——切换会话/开关插件时就会随机出现 Problem。

这正是 0.2.3 发版时 risk 栏预警的「双注册」场景，当时靠探针单挂载验证没暴露。

## 修复（单一所有者 + 防御降级）

1. `cordis.patch.yml`：preset 内嵌 `dev-assistant-tools` 显式 `board: false` ——
   路由唯一所有者是宿主顶层 `dev-workflow-host`（随宿主常驻，不依赖会话）。
2. `index.js` `registerBoardRoute`：`registry.register` 抛「already registered」时
   降级为 no-op（路由已由第一个所有者服务），其余错误照抛。重复挂载不再产生
   红色徽标。

## 本轮踩坑

1. **「risk 栏预警过」不等于「已设防」**：0.2.3 的任务风险栏写了双注册可能，但门禁
   与探针都是单挂载场景，真机双挂载一跑就炸。预警要变成断言或防御代码才算数。
2. **默认值即契约**：`board !== false` 这种「默认开」的分支在单挂载时代无害，引入
   第二种挂载方式时就变成隐式双重行为。多挂载设计下，每个默认值都要重新审。
