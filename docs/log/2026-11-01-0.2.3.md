# 2026-11-01 · 0.2.3 看板入口修复版（宿主顶层挂载）

0.2.2 发布当天追加：修复「装了插件、开关也开了，但侧边栏永远没有『研发看板』入口，
且插件列表无任何报错」的问题。负责人在同一天从安装、刷新、开关、重启一路试到 0.2.2
都没出现入口，最后靠对照隔壁 Deckline（deck-studio）的挂载方式定位根因。

## 根因（这次踩的坑最深）

client 模块组合（宿主 `@deepseek-ai/dsh-client-modules`）按**宿主树里「包名 + 活 fiber」
的 loader 条目**发现浏览器 bundle：`processOne` 只处理 `entry.options.name === 包名` 且
`entry.fiber` 存在、未 disabled 的条目，`resolveMeta` 读不到宿主半边包时**静默置 null 跳过**
（`pkgMeta.set(sourceKey, null)`），整条链路不产生任何错误。

本插件 0.2.2 及之前只在 preset 内嵌挂载（`dev-assistant-tools` 随会话挂载），宿主层
没有本包的 fiber —— 于是：

- `dev_*` 工具在会话里一切正常（会话内挂载）；
- 页面模块图里没有本包 → 看板 UI 永远缺席；
- 无报错、插件列表无同步失败、开关与重启全部无效（结构问题，不是时序问题）。

Deckline 能显示左侧入口，正是因为它的 `cordis.patch.yml` 顶层 `insert` 把自己挂载成
宿主常驻插件。

## 修复

`cordis.patch.yml` 顶层 `insert` 增加宿主级挂载：

```yaml
- id: dev-workflow-host
  name: 'dsh-plugin-dev-workflow'
  config:
    tools: false   # dev_* 工具仍由会话内 preset 的 dev-assistant-tools 负责
    reminder: false
```

`apply()` 的 `config.board !== false` 分支让这次挂载注册只读看板路由
（`/api/dsh-dev-assistant.board`），看板从此不依赖任何会话。

## 本轮踩坑

1. **「装完插件立刻生效」不成立的结构性原因**：HMR/开关只影响已挂载的 fiber；一个
   只活在 preset 里的包，宿主层从来没有过它的 fiber —— 重启也带不进来。发布带
   浏览器 UI 的插件，必须在 patch 顶层挂载包本体。
2. **对照样本是最快路径**：同机已验证可用的插件（Deckline）是最可靠的参照系，
   逐项 diff package.json / patch 结构比读宿主源码猜快得多——两者这次各花一半时间。
3. **桌面 App 的 profile CLI 不可直接操作**（`profile "desktop" is managed exclusively
   by the Electron application`），调试时用 `DSH_HOME` 指到临时目录复制 profile 起探针，
   不碰用户正在跑的实例。
